General instructions

All messages are send over HTTPS to RESTful service in JSON format. Client should set proper HTTP headers and HTTP verbs when sending requests and check for HTTP status codes when evaluate response:

Request HTTP headers:

  • Accept:application/json
  • Content-Type:application/json

Request methods:

  • POST for sending mesages

Response HTTP status codes:

  • 200 OK: valid request, it will be send to upstream server, i.e. bank or operator
  • 422 Unprocessable entity: invalid request due to input validation, it will not propagate further
  • 500 Internal server error: server application error, a bug - they hide we seek

Other notices:

  • use the status field to get response status when available, not HTTP response code, e.g. a transaction may be declined by the acquirer and it will have HTTP 200 OK and status field "declined"
  • note that there may be response fields which aren't a part of the specification, (id, created_at, ...), don't count on them as they may be subject to change without prior notice
  • we will introduce new fields if the requirements changes in the future
  • don't let the client application break if it encounters extra response parameters (mass unrestricted attribute assignment will do this, for example)
  • parametrize the API host root url and API paths, this will be subject to change and will be different between test and production systems
  • response timeout is at 30 seconds and subject to change

Response fields specification for invalid request - 422 HTTP code

Only invalid fields will be reported. Each offending attribute has its entry in json in this form:

{attr1: [error description 1, error description 2, ...], attr2: [error description 1, error description 2, ...]}

For example, if amount is not integer and if systan is not unique response will look like this:

{"amount": ["must be an integer"], "systan": ["must be unique"]}

Request can be also declined even if it is valid in case when certain conditions are met. For example:

  • {"access_token": ["unknown terminal"]} - when terminal is disabled on server
  • {"customer_number": ["unknown customer"]} - if invalid value is entered
  • {"amount": ["credit limit exceeded"]} - credit limit for merchant
  • {"amount": ["amount limit exceeded"]} - limit for single payment

In each of these cases a message should be printed on screen.

digest field specification

The digest field is calculated differently in different API calls, it is used to protect critical API data fields. When the message specification says Digest(a,b,c) what is meant is:

Digest::SHA512.hexdigest(a+b+c)

Integers and boolean values are converted to their string representation.

For example, if message specification says the digest is defined as Digest(terminal_id, terminal_key, active) this means that if terminal_id is integer 12345, terminal_key is string 'secret!1Key' and active is boolean true then the digest is equal to:

Digest::SHA512.hexdigest('12345secret!1Keytrue') => "8f9c98b16a85914..."

systan field specification

The purpose of this integer field is to prevent duplicate transactions.

A common scenario in transaction processing is that network disconnects after the message is sent and before the response arrives. This results in a "declined" status on the client and possibly an approved transaction on the server.

Before you make another transaction with a new systan, you should attempt a reversal using the systan field to reference the last request. The reversal should always succeed, but in case it doesn't it should stop processing transactions until it does.

Systan should be unique for last 24h at least and should reliably increment for +1, this way gaps in systans can be used to trace system issues.

entry_method field specification

This field describes how the PAN was entered into the system, possible values are emv, emv_nfc, magstripe, fallback, keyed_entry

  • emv - the device's chip was used to authenticate the cardholder by inserting the card into the EMV reader, see EMV specification
  • emv_nfc - like emv, but NFC was used to facilitate EMV message exchange, not the connector in the POS
  • magstripe - when a card does not have a chip, possibly identifiable using the "Service Code" field, see https://en.wikipedia.org/wiki/Magnetic_stripe_card
  • fallback - when a card has a chip, EMV was attempted but failed due to chip not being readable by the hardware in 3 attempts and the device proceeded with fallback to magstripe. Common way of going around the EMV by fraudulent merchants is to put the card into the reader upside-down 3 times so the server needs to flag this as a special kind off entry instead of simply calling it 'magstripe'
  • keyed_entry - a last resort, the merchant lets the cardholder enter the data manually on the POS, will be disabled by default

As you can tell, some of the options are more dangerous than others, basically: emv_nfc > emv > magstripe > fallback > keyed_entry preference should be implemented on the POS device.

EMV specification

Be sure to read https://en.wikipedia.org/wiki/EMV

The EMV kernel should provide you with a set of attributes (key, value), for example:

"84":"A0000000049999C000010560", "8F":"04", "82":"5800", "9F02":"000000023398", "95":"0000001000", "9A":"100109", "9C":"00", "9F36":"0001", "9F37":"D8B57618", "9F26":"45B2B2B634ADB290","9F27":"80", "9F10":"0D10A50003020800C75900000000000000FF", "9F34":"410302"

This data may or may not be provided by the hardware using BER-TLV format, see http://chipnpin.blogspot.hr/2012/09/ber-tlv-encoding-of-emv-tags.html and https://stackoverflow.com/questions/18853800/simlpe-tlv-vs-ber-tlv

The server will generally forward from the issuer something like:

"84":"A0000000049999C000010560", "8F":"04", "82":"5800", "9F02":"000000023398", "95":"0000001000", "9A":"100109", "9C":"00", "9F36":"0001", "9F37":"D8B57618", "9F26":"45B2B2B634ADB290", "9F27":"80", "9F10":"0D10A50003020800C75900000000000000FF", "9F34":"410302", "8A":"00"

But don't get confused if it returns just "8A", the rest of the values were simply echoed from the request, you should have those already.

EMV response fields are one of those things we don't control, it's set up by the issuer.

Note that action is required after the response is received and in some cases may require a technical reversal to be sent - most notably when ARPC doesn't match against ARQC, see https://en.wikipedia.org/wiki/EMV#Online_transaction_authorization and subsequent steps (Online transaction authorization, Second card action analysis, Issuer script processing)

Bill payment
Customers paying their utility bills

It allows customers to pay their bills using their customer_number which is unique for each operator. A menu is built from operators array from configuration - merchant can select operator by its name (those that have type set to 'bill'), then customer will enter its customer_number for that operator and the amount he wish to pay. If all is right, server will return current balance for a customer which is printed on receipt along with currency and amount payed.

This message is POSTed to root + URL.

Voucher selling
Customers buying vouchers

It allows customers to buy credits for phones or such. A menu is built from operators array from configuration - merchant can select operator by its name (those that have type set to 'voucher'). Then second menu is built from voucher array - it lists all available vouchers by their name for selected operator (with their amount and currency). Operator and vouchers have 1..n relation, where code and operator_code are keys. After voucher is selected and confirmed, request is sent to server. If all is right, server will return value (code) for that voucher which is printed on receipt along with currency and amount payed.

This message is POSTed to root + URL.
